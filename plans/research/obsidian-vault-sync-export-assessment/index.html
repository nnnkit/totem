Totem export and Obsidian vault sync assessment

Totem's current export is already readable inside Obsidian, but it is not yet an Obsidian-native sync experience. The right first integration is a local vault writer using the File System Access API, not an Obsidian cloud integration, a obsidian:// URI loop, or the Local REST API.

What v2 adds

The v1 thesis below held up under adversarial verification across six integration mechanisms, the competitor field, and every common Obsidian sync transport. This v2 update adds: a verified mechanism scorecard (each load-bearing claim refuted-or-confirmed against primary sources), what the best read-it-later tools actually do and the one pattern Totem must copy, sync-transport safety rules for writing into a folder some cloud daemon is watching, and a concrete change surface mapped to Totem's real files. Thesis

Ship Obsidian as a local destination: Totem writes Markdown files into a user-selected vault folder, then the user's existing Obsidian Sync, iCloud, Dropbox, Git, Syncthing, or other setup moves those files across devices.

Current export fit 7/10

Good Markdown and ZIP structure. Missing direct vault write, stable sync paths, richer properties, media localization, and idempotent update rules.

Short answer

Use local first. There is no reason for Totem v1 to know whether the user uses Obsidian Sync or another cloud provider. Obsidian's model is still local files first; cloud sync is layered behind the vault.

What Obsidian Expects

Official Obsidian docs define a vault as a folder on the user's local file system. Notes are Markdown-formatted plain text files, Obsidian creates a local .obsidian configuration folder, and the app refreshes its vault when external files change. That is the product opportunity: Totem does not need an Obsidian account connection to create useful Obsidian notes.

Obsidian also supports both Markdown links and wikilinks. Since Obsidian explicitly recommends Markdown links when interoperability matters, Totem does not need to convert every link to [[wikilink]] syntax for v1. YAML front matter maps to Obsidian Properties, so Totem should invest there first.

Implication: the integration boundary is the local folder, not a proprietary cloud API. Obsidian Sync creates a remote vault for the user's devices, but Totem should write to the local vault that Obsidian already indexes.

Current Export Audit

Totem has a strong export foundation. The library export writes one Markdown file per bookmark, a Markdown index, CSV, JSONL canonical data, checksums, and a manifest. Reader export can copy or download Markdown for a single item. The export tests passed during this research pass: 51 passed across quick-export.test.ts and article-export.test.ts.

How Vault Sync Should Work

The first Obsidian integration should be a manual local sync destination. It should not ask for an Obsidian account, should not try to write to Obsidian's remote vault, and should not assume which cloud provider the user uses.

Connect flow
  1. User clicks Connect Obsidian vault.
  2. Totem calls showDirectoryPicker({ mode: "readwrite", id: "totem-obsidian-vault" }).
  3. Totem checks for .obsidian as a vault signal, but allows "use this folder anyway" if absent.
  4. Totem stores the FileSystemDirectoryHandle in account-scoped IndexedDB.
  5. Every sync run calls queryPermission and requestPermission if needed.
Write flow
  1. Hydrate missing full content if the user chooses full sync.
  2. Render notes with an Obsidian-specific Markdown renderer.
  3. Write only under a Totem-owned folder, for example Totem/.
  4. Update an internal manifest with paths, tweet IDs, hashes, and last sync time.
  5. Open the result with an obsidian://open URI when the user asks.

# Guide to local-first bookmarks

[Open on X](https://x.com/example/status/1792345678901234567)

...rendered tweet, thread, article, media links, highlights, and notes...

Local or Cloud?

For Totem v1, the answer should be local. Obsidian cloud sync is still organized around local vaults connected to remote vaults. The local folder is the thing a browser extension can safely and transparently write. Obsidian Sync, iCloud Drive, Dropbox, Syncthing, Git, Remotely Save, or another provider is the user's separate transport layer.

Question Recommendation Reason
Should Totem detect whether the vault uses Obsidian Sync? No for v1. The browser sees a folder handle, not a reliable provider identity. Detection would be fragile and unnecessary.
Should Totem write directly to Obsidian's cloud remote vault? No. Obsidian's public model is local files plus optional Sync. There is no product need to bypass the user's local vault.
What should the user-facing copy say? "Totem writes Markdown into your local vault. If your vault already syncs, Obsidian or your sync provider will sync those files." This keeps Totem's local-first promise and avoids implying Totem runs a cloud sync service.
What if the user uses multiple devices? Manual sync from one primary device in v1; warn before a second Totem install writes to the same managed folder. Multiple writers against the same folder can create conflicts, especially when cloud sync is also moving files.
Obsidian itself warns that syncing is not backup and recommends care when combining Obsidian Sync with cloud storage providers. Totem should be framed as a file writer, not another competing sync provider.

Verified Mechanism Scorecard

Six ways an extension can get content into a vault were researched in parallel and each mechanism's riskiest claim was then handed to an independent skeptic to refute against primary sources. The picture is unusually clear: only one mechanism scales to thousands of repeatable writes from a Chromium extension.

showDirectoryPicker → write .md		 Primary path The new-tab override is a full top-level document, which is the working side of the documented picker bug. Directory handles are structured-cloneable and persist in IndexedDB. No server, works whether or not Obsidian is open, no rate limit. Chromium-desktop only, which is exactly Totem's surface.

Four corrections the verification pass produced

  • The picker bug is popup-only, not extension-wide. showDirectoryPicker() throws AbortError in an action popup even after the user picks a folder (Chromium 40240444 / WICG #314, still open July 2025), but succeeds in a full tab. Totem's new-tab page is a full tab — so it is unaffected, provided Totem never triggers the picker from a popup.
  • The handle survives a restart; the write permission does not. A handle reloaded from IndexedDB typically reports queryPermission === 'prompt'. Regaining write access needs requestPermission({mode:'readwrite'}) inside a user gesture — it cannot be done silently or from the MV3 service worker. So re-sync must be a click on the new-tab page.
  • "Allow on every visit" for a chrome-extension:// origin is unconfirmed. Chrome 122+ persistent permissions exist, but no primary source confirms the indefinite grant is honored for extension origins specifically (PWAs get it by default). Design for a possible per-session re-prompt; treat unattended re-sync as a thing to verify empirically, not assume.
  • File writes are not guaranteed atomic across devices. The spec says changes land on close() and are "typically" written via a temp file, but atomicity is non-normative ("try to ensure"). So every note must be self-contained — no note may depend on another arriving first — because every sync transport propagates files one at a time.

What the Best Tools Actually Do

Across Readwise, Readwise Mirror, Matter, and Raindrop, the dominant bulk-sync shape is identical and battle-tested: an idempotent, ID-keyed write loop with a last-sync cursor. The only thing Totem should drop is their shared weakness — the cloud API.

The pattern to copy
  • Stable per-item ID in YAML frontmatter as the join key (Raindrop's raindrop_id). For Totem this is tweet_id. Join on the property, not the filename, so user renames never trigger re-creation.
  • A content map + last-sync cursor (Matter's contentMap: id → file): on each run decide create / update / skip per item.
  • Content-hash skip so steady-state re-syncs touch only changed notes — a huge win at thousands of items and minimal sync churn.
  • Choose a write model: append-only protects hand edits (official Readwise); mirror/overwrite guarantees convergence (Readwise Mirror, ~5,067 highlights in ~20s) at the cost of editability. Totem can default to overwrite-in-a-managed-subfolder.
Totem's structural advantages
  • No API, so no rate limit. Every surveyed tool throttles around a cloud quota (Raindrop 120/min); Totem reads from local IndexedDB and is bounded only by per-file write overhead.
  • No backend to lose. Omnivore proves cloud-dependent integrations have a catastrophic single point of failure; Totem's feature survives indefinitely because it writes from local data.
  • A vault is just a folder of .md. Obsidian auto-refreshes external changes, so direct file writes are a first-class, supported ingestion path — no plugin, no running app required.
Direct competitors exist (an X Bookmarks Sync Obsidian plugin, Tweet-to-Markdown, a x-bookmark-to-obsidian Chrome extension), but none has shipped a polished, local-first, batch new-tab experience. The niche is contested, not taken.

Sync Transport: Assume the Worst, Write Safe

Totem cannot detect which engine (if any) watches the chosen folder — there is no API to ask "is this iCloud or Dropbox?", and a folder can be watched by more than one. From the sync engine's view, a file Totem writes is indistinguishable from one the user typed, so it will be replicated, conflict-resolved, and — critically — its deletion will be propagated. The only safe design is provider-agnostic and defensive.

Transport Conflict behavior Risk to an external writer
Obsidian Sync (paid) Markdown-aware merge (diff-match-patch); optional "create conflict file" Best case. Hand-editing a Totem note while Totem rewrites it can duplicate text — mitigated by a "do not hand-edit" managed subfolder.
iCloud Drive Silent last-writer; duplicate "(1)" files Hostile. The daemon uploads mid-write (propagates partial states); "Optimize Storage" can dehydrate files so they look deleted.
Dropbox / Google Drive / OneDrive Conflicted-copy files; no content merge Desktop-OK, weak/again-risky on mobile. OneDrive Files On-Demand and Drive have documented "looks deleted / permanent loss" paths.
Syncthing / Git Keeps both versions (.sync-conflict / merge markers) Safer — nothing silently lost. Git mobile cannot resolve conflicts; raw <<<<< markers can appear.
LiveSync / Remotely Save (plugin) CouchDB multi-revision / plugin-level diff Ingests Totem's writes only when Obsidian is open and re-scans. A big import may need the user to open Obsidian once.

The safe-write rules (ordered by importance)

  1. Write only inside a Totem-owned subfolder (<vault>/Totem/). Never touch files outside it. Tell the user it is Totem-managed and not to hand-edit it.
  2. Idempotent create-or-update keyed by tweet ID embedded in both filename and frontmatter; join on the frontmatter ID.
  3. Never delete. If a bookmark disappears upstream, mark it (totem_status: removed) rather than removing the file — a delete would replicate to every device, and placeholder/dehydrated files only look deleted.
  4. Atomic, self-contained files. Write via createWritable (flushes on close); make every note independently valid so a partially propagated batch never breaks.
  5. Manifest is canonical in IndexedDB ({tweetId → filename, contentHash, lastWritten}), never authoritatively in the vault, so a stale/dehydrated vault manifest can never drive a deletion.
  6. Throttle/batch writes with the content-hash skip, so steady-state syncs touch only changed notes and minimize the window for a daemon to read partial state.

Conflict policy

  • Write only under Totem/; never touch user-authored files elsewhere.
  • If a note exists and its hash matches the manifest, Totem may overwrite it with updated generated content.
  • If a note exists and the user has changed it, preserve it and write the new generated version under Totem/Conflicts/ or ask before replacing.
  • Do not delete notes in v1. If a bookmark disappears or becomes unavailable, mark it in properties on safe updates.
  • Store a device ID in the manifest and warn if another Totem install appears to own the folder.

Phased Recommendation

Phase 1: Obsidian export preset

Add a second ZIP shape that produces Totem/ with stable tweet-ID filenames, richer YAML, an index note, and highlights in Markdown. This is low-risk because it reuses the current ZIP path.

Phase 2: Manual local sync

Add "Sync to Obsidian vault" using a selected folder handle. Keep it user-triggered first. Use the same renderer as the Obsidian ZIP preset.

Phase 3: Digest workflows

Create daily or saved-search digests under Totem/Digests/. Digests are more useful than dumping thousands of raw bookmark notes without context.

Phase 4: Optional plugin or paid cloud

Only after local sync is useful, consider an Obsidian plugin, scheduled digests, Notion, Readwise, Sheets, or other cloud adapters.

Open Decisions

  • Should v1 write one note per bookmark, digest notes only, or both? My recommendation: both, but default the UI around digests.
  • Should notes include downloaded media? My recommendation: external media links in v1, local attachments later.
  • Should user edits be supported in generated notes? My recommendation: yes, by hash-based conflict protection, not by trying to merge Markdown intelligently in v1.
  • Should Totem auto-sync in the background? My recommendation: no for v1. Directory permissions and multi-device conflict risk make manual sync the right starting point.
  • Should current ZIP export change? My recommendation: keep v1 frozen; add an Obsidian preset rather than breaking the importable archive contract.
