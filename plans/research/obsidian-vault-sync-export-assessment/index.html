Syncing Totem bookmarks into an Obsidian vault

Folder-and-vault sync is not only possible, it is the right shape for a local-first extension. Totem should write Markdown straight into a user-picked vault folder using the File System Access API — not an Obsidian account, a obsidian:// URI loop, or the Local REST API.

The short answer

An Obsidian vault is just a folder of Markdown files, and Obsidian auto-refreshes when external files change. So Totem needs no Obsidian account, no plugin, and no server: it can write .md files into a folder the user chooses, and the user's existing sync — Obsidian Sync, iCloud, Dropbox, Git, Syncthing — carries them across devices.

Thesis

Ship Obsidian as a local destination. Totem writes Markdown into a user-selected vault folder; the user's own sync layer moves the files.

Current export fit 7/10

Good Markdown and ZIP structure. Missing a direct vault write, stable sync paths, richer properties, and idempotent updates.

Use local first

There is no reason for v1 to know whether the user runs Obsidian Sync or iCloud. Obsidian's model is local files first; cloud sync layers behind the vault.

The recommendation in one line

A File System Access local vault writer, run from the new-tab page, idempotent and keyed by tweet ID. Six integration mechanisms were researched and each one's riskiest claim was handed to an independent skeptic to refute against primary sources. Only one scales to thousands of repeatable writes from a Chromium extension.

MechanismBulk-sync verdict
File System Access APIPrimary path — no server, no rate limit, works whether Obsidian is open or not
obsidian:// URISingle-item only — one note per call, silent failure past ~2k chars, steals focus
Local REST API pluginPower-user opt-in — self-signed cert, desktop-only, Obsidian must be open
Cloud-API round-tripAvoid — Omnivore's plugin died when its API went offline

The full six-way comparison with verdicts is on the mechanism scorecard.
