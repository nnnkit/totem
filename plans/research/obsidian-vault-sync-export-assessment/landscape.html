What Obsidian expects, and where Totem stands

Totem's export is already readable inside Obsidian. It is not yet an Obsidian-native sync experience. The integration boundary is the local folder, not a cloud API.

Findings Current export fit: 7/10

What Obsidian expects

Official Obsidian docs define a vault as a folder on the user's local file system. Notes are Markdown-formatted plain-text files, Obsidian keeps a local .obsidian configuration folder, and the app refreshes its index when external files change. That is the product opening: Totem does not need an Obsidian account connection to create useful Obsidian notes.

Obsidian supports both Markdown links and wikilinks, and explicitly recommends Markdown links when interoperability matters — so Totem need not convert every link to [[wikilink]] syntax for v1. YAML front matter maps to Obsidian Properties, so that is where to invest first.

Implication: the integration boundary is the local folder, not a proprietary cloud API. Obsidian Sync creates a remote vault for the user's devices, but Totem should write to the local vault that Obsidian already indexes.

Current export audit

Totem has a strong export foundation. The library export writes one Markdown file per bookmark, a Markdown index, CSV, JSONL canonical data, checksums, and a manifest; reader export can copy or download Markdown for a single item. The export tests passed during this research pass (51 passed across quick-export.test.ts and article-export.test.ts).

The integration boundary

Two gaps are the whole story: there is no direct vault write, and there is no idempotency layer. The renderer, the YAML, and even a showSaveFilePicker + createWritable path already exist. The work is to add a directory destination and an ID-keyed update layer on top of what ships today — which is exactly what the rest of this report specifies.
