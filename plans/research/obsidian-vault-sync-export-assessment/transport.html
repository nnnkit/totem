Sync transport: assume the worst, write safe

Totem cannot detect whether iCloud, Dropbox, Git, Syncthing, or Obsidian Sync is watching the folder it writes to. So it must write in a way that survives all of them — the safe-write rules below are not optional polish, they are the contract.

The transports Totem can't see

Each sync engine a user might run behind their vault has a different failure mode. Totem writes blind to all of them, so the design must assume the harshest combination.

TransportBehavior to surviveRisk if naive
iCloud DriveMay evict files to the cloud and download on access; renames can lag.A partial read of an evicted file looks like an empty note.
DropboxWatches the folder live; uploads on every byte change.Mid-write reads ship a half-written file to every device.
Obsidian SyncIndexes and syncs on file-change events.Rapid rewrites churn the sync log and can trigger conflict copies.
Git (Obsidian Git)Commits on a schedule; diffs every line.Reordered YAML keys or timestamp churn create noisy, useless diffs.
SyncthingBidirectional; resolves conflicts by creating .sync-conflict copies.Two devices writing the same path spawn duplicate conflict files.

The safe-write rules

Six rules make a write survive any of the transports above. They are cheap to implement and they are the difference between a sync that users trust and one that quietly corrupts notes.

  1. Write atomically. Write to a temp file in the same directory, then rename into place. A watcher never sees a half-written note — it sees the old file, then the new one.
  2. Make writes deterministic. Stable YAML key order, stable formatting, no volatile timestamps in the body. Re-rendering an unchanged item must produce byte-identical output so Git and Sync see no change.
  3. Skip no-op writes. Compare a content hash before writing; if nothing changed, don't touch the file. This is what keeps Dropbox and Obsidian Sync quiet.
  4. Own a subfolder, never the vault root. Write only inside a Totem-owned folder so a conflict copy or a stray file can never collide with the user's own notes.
  5. Never delete. Removing a bookmark in Totem must not delete the vault note. Orphans are the user's to clean up; silent deletion is unforgivable.
  6. Keep the manifest canonical in IndexedDB, not the vault. The source of truth for what Totem has written lives in the extension, so a sync conflict on a note never corrupts the index of what exists.
