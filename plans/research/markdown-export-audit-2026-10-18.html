Markdown export audit

2026-10-18 · Tested against 60 real bookmarks and 2 TweetDetail payloads captured from a logged-in X session, run through the real parser and exporter (parseBookmarkPagePayload, then resolveReaderExportArticle, then articleToMarkdown).

Root cause

Plain tweets and threads were first turned into markdown-ish text. That text was then fed back through the article pipeline, which ran heading detection, paragraph re-flow, escaping and link regexes over it a second time. Most of the visible breakage came from this second pass. Tweets now get a dedicated renderer (src/lib/export/tweet-markdown.ts) that works from structured data and skips the article heuristics.

Still not supported

  • Polls: the parser doesn't read poll cards (poll2choice_*). None of the 60 sampled bookmarks had one.
  • Non-summary cards (player, app, unified_card) are ignored by parseCard.
  • Direct MP4 links: the parser stores videoUrl, but export only links to the post on X.
  • Reply prefixes: leading @a @b handles stay in the text. X hides them using display_text_range.
  • Not verified on real data: article image galleries and embedded-post entities. Only LINK, header and list blocks appeared in the sample.
  • Reader UI still doesn't show bold/italic for long posts. Only export uses textStyles.
  • PDF export still goes through the old plain-text path.
  • Bold/italic for posts already saved: it only shows up once the post's detail is fetched again. The stored rows were parsed before textStyles existed.
  • ZIP export of X Articles never opened in the reader: these export only the Bookmarks-feed preview, which is truncated and runs through the heading heuristics. This was already the case before this change.
